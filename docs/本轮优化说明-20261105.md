# 零售BI助手：本轮优化与验证

本轮目标：让有限范围的零售取数原型保留用户提出的条件，并在无法回答时说明原因，便于后续实际操作和学习。版本0.4.0，全部使用合成数据。

## 本轮修复

| 原有问题 | 现在的处理 |
| --- | --- |
| “2024年线上销量最高的三个品类”丢失条件 | 年份、渠道、Top 3都写进计划及SQL |
| 只写11月默认当成2024年11月 | 请求补全年份，不替用户决定关键条件 |
| 今年被忽略，实际取历史数据 | 按北京时间解释今年；超出记录范围则说明不足 |
| “为什么下降”返回总销售额，还被标为通过 | 说明描述性数据不能确定原因，请求明确对比 |
| 同问销售额和订单数只返回一个指标 | 支持该组合，逐一检查计划字段 |
| 多个月份被当成同时满足 | 同字段多个值取并集，不同字段取交集 |
| 部分复购、环比查询忽略筛选 | 在实际统计范围内筛选；跨年上月正确定位 |
| 百分比简单限制在-100%到100% | 增长率可超过100%，亏损毛利率可低于-100% |
| “高/100分”容易被误认成正确率 | 改为结构检查通过、需复核、需要补充、数据不足 |
| 配好key后可能自动在线 | App、CLI和评测默认离线；不预设模型与报价 |

在线实验仍受同一语义计划范围约束。模型SQL的结果与该计划编译的SQL不同，会标为需复核、暂停图表和结论。这只用模拟模型测试，未做真实模型评测；计划本身若理解错了，两者仍可能一起错。

## 仍然存在的边界

- 这是有限规则解析的原型。已覆盖的条件会保留；未识别到的长尾条件仍可能遗漏，使用结果前需核对可见的分析计划。
- 数据为2023—2024年合成记录。最早和最晚订单日期只说明观察到的跨度，不能证明期间每一天、每个渠道都有完整数据。
- 不支持多轮上下文、预测、因果归因、日级范围、最近N天、任意SQL或所有指标组合。部分不支持的表达会主动请求改写。
- 顾客数默认是顾客表人数，不能混同时间/渠道下的购买人数。复购是所选范围内下单超过一次的人数，不是复购率。
- 未验证真实用户节省时间、独立任务完成率、企业部署价值及在线模型效果。只读护栏不等于完整的企业权限管理。
